# Ubuntu 22.04 / N100 飞镖视觉环境与联调说明

这份说明面向当前 Dart 项目。目标是在 Ubuntu 22.04 的 N100 小电脑上，使用海康 MV-CS020-10UC 相机和 MVL-HF1229M-6MPR 镜头，完成实时采集、原有传统视觉识别与跟踪、电控通信和屏幕显示。按用户选择，入口切换到仓库已有的传统识别分支；检测算法内部、跟踪、误差计算和串口处理逻辑保持原样。

**相机已接入，用户已确认 MVS 能正常采集并显示画面；电控尚未完成接入验证。项目编译和离线传统识别检查已通过，Dart 下的相机显示、真实目标识别跟踪和电控通信仍需继续验收。**

用户已确认的信息：串口使用 `921600 8N1`，相机沿用原项目的安装方向。因此本次保留波特率、数据格式及图像旋转设置；现场仍需用实际画面和目标移动确认误差方向。

## 1. 先理解程序实际怎么运行

实时运行时，程序主要沿以下路径工作：

```text
电控发送有效 CarData 数据包
             ↓
海康相机取图 → 旋转图像 → 原有 GreenLightDetector 传统识别
                                 ↓
                  选择与跟踪目标 → 计算像素误差
                                 ↓
                   向电控发送 VisionData 数据包

同时显示：img / mouse / track
```

当前 `main.cpp` 使用 `Detect("traditional")`，在 `src/detect/src/Detect.cpp` 中创建仓库原有的 `GreenLightDetector`，由 `src/detect/src/traditional/traditional_detect.cpp` 实施传统识别，不加载 Katrin 模型，也不进行神经网络推理。本次只选择已有分支，没有重写传统识别算法。

原传统算法先比较绿色通道与红、蓝通道的差值，再结合 HSV 颜色范围和亮度增强，经过形态学开运算减少噪声，使用轮廓与 blob 寻找候选灯，按面积、半径、圆形程度及局部对比度等条件筛选，再做颜色、空间过滤和邻近候选合并。具体阈值和实际执行步骤以原源码为准，本次不调整。

这些传统阈值主要写在 `GreenLightDetector` 的构造函数和 `detect()` 内；`detect.json` 中的 OpenVINO 置信度等设置只供模型分支使用，不能当作当前传统检测的调参入口。

仓库中的 Katrin 是另一条 OpenVINO 路径的模型，`.xml` 保存模型结构，`.bin` 保存权重；上轮对它做过离线测试，但这不代表当前传统模式正在使用它。

N100 的实际运行帧率需要接入相机、目标和电控后测量；不能把相机请求的采集帧率直接当作识别帧率。

### DUMP、实时采集、录像分别是什么意思

| 配置 | 数据来源和用途 |
| --- | --- |
| `DART_DUMP=ON` | 原意是读取已有 MCAP 文件回放，但原分支有头文件和数据字段兼容问题。本次没有修改回放逻辑，配置时会明确报错，不支持直接切回该模式。 |
| `DART_DUMP=OFF` | 启用真实相机、检测、跟踪、鼠标显示等实时任务，并与电控通信。 |
| `DART_CAPTURE=ON` | 在实时运行基础上，增加保存 MCAP 数据的任务。 |
| `DART_CAPTURE=OFF` | 实时运行但不保存 MCAP，适合当前先打通相机和电控的阶段。 |
| `DART_WITH_DAHENG=OFF` | 不构建大恒相机支持，避免本次只使用海康却依赖另一家 SDK。 |

本次采用 `DART_DUMP=OFF`、`DART_CAPTURE=OFF`、`DART_WITH_DAHENG=OFF`。关闭录像不等于关闭实时识别或屏幕显示。

## 2. 环境与编译配置

主要依赖包括 C++ 编译器、CMake 3.25 或更高版本、带图形窗口支持的 OpenCV、OpenVINO C++ Runtime / 开发文件、海康 MVS 相机 SDK、FlatBuffers，以及项目 CMake 所需的其他库。Ubuntu 22.04 自带的软件版本不一定满足源码的最低要求，要以构建时实际使用的版本为准。

虽然当前运行传统识别，现有 `Detect` 类仍共同编译两种分支，并共享 `OpenvinoInfer::Light` 等类型，因此 OpenVINO 仍是构建和链接依赖。保留这个依赖不表示传统模式执行神经网络推理；本次没有拆分或重构检测类。

本项目 `config/autogenerated_flatbuffers/` 已有自动生成的头文件，其 FlatBuffers 版本需要与所用开发头文件兼容。本次采用项目本地前缀 `.deps/flatbuffers-25.2.10`，让当前项目使用匹配版本，避免为了本项目替换整个系统的 FlatBuffers。安装脚本只构建对应库和头文件，不安装 `flatc`，也不重新生成仓库中已有的头文件。

`CMAKE_PREFIX_PATH` 是告诉 CMake 到哪里找依赖的提示；它不是相机配置。`.deps` 内的构建产物也不是检测或控制算法。

需要在另一台电脑重现本地 FlatBuffers 依赖时，可在准备好 `curl`、`tar`、`sha256sum`、CMake、Ninja 和 g++ 后运行下面的脚本。它会从官方 GitHub 下载固定版本，核对 SHA256，再安装到项目 `.deps`，不需要 `sudo`：

```bash
cd /home/yc-mini/Dart
bash scripts/setup_flatbuffers.sh
```

下面的命令以当前项目路径 `/home/yc-mini/Dart` 为例。在依赖准备完成后执行：

```bash
cd /home/yc-mini/Dart
cmake -S . -B build \
  -DCMAKE_PREFIX_PATH="$PWD/.deps/flatbuffers-25.2.10" \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
  -DDART_DUMP=OFF \
  -DDART_CAPTURE=OFF \
  -DDART_WITH_DAHENG=OFF
cmake --build build --parallel 2
```

`-S .` 指定当前目录是源码目录，`-B build` 把生成文件和程序放进 `build`。`--parallel 2` 限制并行编译任务数，减少小电脑在编译时的内存压力。修改 CMake 选项后要重新执行配置和构建，不能只重启旧的可执行文件。

当前 CMake 已提示查找本机安装的 OpenVINO 开发配置，启动脚本也会补充常见 SDK 动态库目录；按当前安装位置运行不需要额外 `source` OpenVINO 的环境脚本。换电脑或改变 SDK 安装目录后，应重新核对 CMake 查找结果和动态库路径。

## 3. 海康相机：哪些参数真的生效

相机类型来自 `config/json/sensors.json` 中的 `camera.type`，当前为 `hikrobot`。但海康的采集参数并没有全部从 JSON 读取。主要初始化设置在 `src/sensors/src/hikrobot/HikRobot.cpp` 的 `cameraInit()` 中：

| 设置 | 当前原始值 | 含义 |
| --- | --- | --- |
| 枚举设备 | `MV_USB_DEVICE` | 使用海康 USB 相机 SDK 路径。 |
| `TriggerMode` | `OFF` | 连续取图，不等外部触发。 |
| `PixelFormat` | `BayerRG8` | 相机输出 Bayer 原始图，程序转成 BGR 图像。 |
| 帧率使能 | 开启 | 向相机设置采集帧率目标。 |
| 帧率目标 | `250.0` | 请求值；是否被设备接受、实际多少帧需现场检查。 |
| `Width` / `Height` | `384` / `640` | 从传感器截取的 ROI 尺寸。 |
| `OffsetX` / `OffsetY` | `680` / `0` | ROI 在传感器上的起点。 |
| 初始化曝光 | `3000 µs` | 相机打开时设置。 |
| 初始化增益 | `8.0` | 相机打开时设置。 |

这组值是原项目的设置，并非根据 MV-CS020-10UC 和新镜头重新测量得到的参数。本次保留它们。硬件接上后，需要确认设备接受这些设置、目标位于 ROI 内，以及画面亮度和清晰度满足识别需求。仅在 MVS 中更改参数，可能会在程序下次启动时被这些初始化调用覆盖。

### 图像方向

`getImage()` 在拿到 `384×640` 的 BGR 图后，依次执行 `transpose`、`flip(..., -1)` 和 `flip(..., 1)`，合起来相当于逆时针旋转 90°，最终为 `640×384`。传统检测直接接收这张旋转后的图像。

用户已确认沿用原项目的相机物理安装方向，因此保留这组旋转。屏幕中的横向、纵向和电控所说的左右方向，要结合这次旋转来理解。实机验收时若发现画面方向不对，先记录安装方向及当前显示结果，再决定是否需要单独配置方向；不要同时试改多个方向和误差符号。

### JSON 中的字段与海康实际读取情况

| JSON 字段 | 当前海康路径中的作用 |
| --- | --- |
| `camera.type` | 生效，用于选择海康或大恒实现。 |
| `camera.drop_time` | 生效，作为持续取图失败的超时判断参数，单位按当前代码换算为秒。 |
| `camera.hikrobot.exposure.red_exposure` / `blue_exposure` | 在模式或颜色切换判断时读取并设置曝光。 |
| `camera.width` / `height` / `channels` | 不控制当前海康初始化的 ROI；ROI 在 C++ 中设置。 |
| `camera.hikrobot.exposure.auto` / `normal` | 当前海康初始化没有用它们配置自动曝光或初始曝光。 |
| `camera.hikrobot.gain` | 当前海康初始化没有从这里读取增益。 |
| `camera.hikrobot.offset` | 当前海康初始化没有从这里读取 ROI 偏移。 |
| `camera.hikrobot.white_balance` | 当前海康初始化没有从这里读取白平衡。 |
| `camera.hikrobot.cam` / `cam1` / `dis` | 当前识别、跟踪、像素误差计算路径没有使用这些内参或畸变矩阵。 |

当前相机代码把 `my_color` 固定为 `0`，首次进入相应模式时会选择 `red_exposure`，现有 JSON 值是 `4500 µs`。所以不要看到初始化中的 `3000 µs` 就认为整次运行曝光一定保持为 3000。

镜头型号不能直接给出这台相机和镜头组合的准确内参。内参通常还与实际成像、焦距设置、ROI 等有关。这里保留原 JSON 值，不代表已经为这套硬件完成标定。当前像素误差链路也没有实现利用这些内参把误差换算为角度。

## 4. 先用 MVS 单独验证相机

项目当前每次取图前都要等电控包。想先验证相机和镜头，可以使用海康官方 MVS 客户端；它不依赖本项目的串口协议。

1. 把相机接入小电脑的 USB 3 接口，确认连接、供电和线缆正常。
2. 在 Ubuntu 本地图形桌面中打开已安装的 MVS。使用适合本机 `x86_64` 架构的 Linux 软件包；下载入口见[海康机器视觉官方客户端下载中心](https://www.hikrobotics.com/cn/machinevision/service/download/?module=0)。
3. 刷新设备列表，找到并打开 MV-CS020-10UC，记录型号和序列号。
4. 在采集控制中选择连续采集、关闭触发，再开始预览。不同 MVS 版本的按钮位置和名称可能不同。
5. 先确认有稳定画面，再调整镜头对焦和光圈，观察引导灯是否清楚、是否过曝。
6. 记录相机当前像素格式、ROI、曝光、增益及实际采集帧率。若要模拟本项目采集条件，再核对上一节的固定参数。
7. 停止采集并关闭设备连接，再启动 Dart，避免两个程序同时占用设备。

MVS 的连接和采集用途及版本界面差异，也可参考[海康 USB3.0 面阵相机官方用户手册](https://www.hikrobotics.com/en2/source/vision/document/2023/8/18/UD31198B_USB3.0%20Area%20Scan%20Camera%20User%20Manual_V2.4.0_20230307.pdf)。

MVS 能预览，只能说明相机采集这一步已经通过；项目中的传统识别、跟踪、电控协议还需继续验收。

## 5. 与电控对齐串口协议

`config/json/sensors.json` 的当前串口配置为 `/dev/ttyACM0`、`921600`、8 数据位、1 停止位、无奇偶校验，即 `921600 8N1`。用户已确认波特率和数据格式正确，保留现有值。设备路径必须根据实际接入结果确认。`/dev/ttyACM0` 可能因插拔顺序而变化；后续可以使用已确认设备的稳定标识或规则固定名称。

当前 `SerialPort.cpp` 将奇偶校验固定为 `N`，不能仅改 JSON 就让当前代码支持另一种校验方式。串口访问权限、设备路径和波特率都必须正确，才可能收到有效包。

结构定义在 `src/utility/inc/global/Struct.hpp`。两个结构均使用 `packed`，没有结构体对齐填充。N100 端直接复制内存，电控要约定相同字段顺序、小端数值编码和 32 位浮点表示。

### 电控 → 视觉：CarData，8 字节

| 字节偏移 | 字段 | 长度 | 现有含义 |
| --- | --- | --- | --- |
| 0 | `header` | 1 | `0xA5`。 |
| 1 | `mode` | 1 | 注释约定：0 不开自瞄不录像；1 自瞄且录像；2 录像。实际行为还要以各模块代码为准。 |
| 2 | `CRC8` | 1 | 对前 2 字节计算的 CRC8，作为前 3 字节的最后一字节。 |
| 3 | `status` | 1 | 电控状态，具体枚举需双方确认。 |
| 4 | `number` | 1 | 飞镖编号，原配置使用 0～4。 |
| 5 | `dune` | 1 | 注释约定：0 完全展开；1 完全关闭；2 正在进行。 |
| 6～7 | `CRC16` | 2 | 对前 6 字节计算的 CRC16，低字节先放、高字节后放。 |

2026-11-05 按用户要求仅修改视觉端：`receive()` 对完整 8 字节包同时检查 `0xA5`、前 3 字节的 CRC8 和整帧 CRC16，全部通过才更新 `CarData`。CRC8 初值为 `0xFF`；CRC16 初值为 `0xFFFF`，计算方式已对齐用户提供的电控 `crc.c`（高字节索引、左移更新）。电控文件没有修改。

**电控必须持续发送正确格式的数据。** `HikRobot::getImage()` 每次取一帧前都会循环等待 `receive()` 成功。只发送一次启动包不够。本次在 CRC 校验前增加了读入长度上限、读取结果和完整帧长度检查，避免短包造成负下标访问；完整的跨次读取拼包机制仍待后续处理，因此包边界和实际收发频率需要现场验证。

### 视觉 → 电控：VisionData，9 字节

| 字节偏移 | 字段 | 长度 | 当前实际含义 |
| --- | --- | --- | --- |
| 0 | `header` | 1 | `0xA5`。 |
| 1 | `CRC8` | 1 | 对前 1 字节 `A5` 计算 CRC8，当前结果为 `A5`。 |
| 2～5 | `yaw_error` | 4 | `float` 类型的像素误差。 |
| 6 | `target_status` | 1 | 0 丢失，1 找到目标。 |
| 7～8 | `CRC16` | 2 | 对前 7 字节计算，低字节先发，高字节后发。 |

发送时先填 CRC8，再填覆盖前 7 字节的 CRC16；这样 CRC16 会覆盖最终的 CRC8 字节。CRC8 函数已支持包含校验字节在内的总长 `2`。两个方向的 CRC8 总长不同：CarData 使用 `3`，VisionData 使用 `2`。CRC16 分别使用整帧总长 `8` 和 `9`。

当前对齐电控实现的示例（均已包含 CRC8、CRC16）：

```text
电控→视觉，mode=1、status=0、number=1、dune=0：
A5 01 CE 00 01 00 A9 19

视觉→电控，yaw_error=0、target_status=0：
A5 A5 00 00 00 00 00 A3 65
```

这些向量使用所提供电控文件的具体算法。原视觉右移算法算出的 `B2 66` 等旧 CRC16 不再适用。不能仅按“CRC16”名称选择其他变体；双方需要对齐查表、初值、更新步骤、覆盖范围和尾部字节顺序。

### yaw_error 的单位与方向

原跟踪代码实际计算的是：

```text
yaw_error = begin - 目标中心 y - group[choice]["0"] - group[choice][number]
```

`begin` 来自 `config/json/ktrack.json`，`group` 和 `choice` 来自 `config/json/track.json`。`目标中心 y` 使用当前目标中心的原始坐标，不是滤波后绘图点 `aim.y`。

所以虽然字段名叫 `yaw_error`，其单位仍然是**图像像素**，没有转换成角度、弧度或编码器值。图像已按原代码旋转，中心 y 对应哪个物理方向，需要结合相机安装确认。电控应先接收并观察数值，用目标沿已知方向移动来核对正负，再接入自身控制环。

另一个值得学习的行为是：跟踪到目标并且 `number=0`、`mode=0` 时，原代码会把当前目标中心 y 写入 `ktrack.json` 的 `begin`。这属于现有基准记录流程。运行时这些配置文件可能因此产生改动；它们与本次环境配置时的修改应分别理解。

程序开始运行后，会向电控发送跟踪结果。当前程序没有单独的“只显示但禁止串口发送”配置。手动终端启动时使用 `Ctrl+C` 结束进程；关闭一个图像窗口不等于结束整个程序。

### 按阶段验收，定位问题更容易

1. **环境与构建：** CMake 找到正确版本的依赖，程序能够完成编译链接。
2. **相机单独预览：** MVS 能找到本机相机并连续显示清晰画面，记录设备序列号和参数。
3. **电控收发：** 确认实际串口设备、权限、`921600 8N1` 或双方约定值、收发帧长度和 CRC 细节，电控持续发包。
4. **项目实时画面：** 手动启动后出现并刷新 `img`，确认视野、亮度和方向，再检查 `mouse`。
5. **识别与跟踪：** 绿色引导灯目标位于 ROI 内，传统检测能检出目标，`track` 中框选、目标状态和丢失恢复表现可解释。
6. **误差验证：** 电控读到 9 字节返回包；沿已知方向移动目标，核对像素误差大小、正负、基准记录和飞镖编号补偿。
7. **最后验证自启动：** 手动运行稳定后，再按需要安装桌面启动项，测试登录后的启动、日志和退出方式。

常见现象可以这样理解：

| 现象 | 优先检查 |
| --- | --- |
| 一直输出 `don't have data` / `don‘t have data` | 电控有没有持续发包、串口是否正确、CRC8 是否正确；此时还不能据此判断相机坏了。 |
| `ioctl: Bad file descriptor` | 串口未成功打开：设备路径、权限或设备连接。 |
| `No Devices Found` | 相机连接、MVS 能否枚举、SDK USB 权限、设备是否被其他程序占用。 |
| `MV_CC_Set... fail` | 对应的像素格式、ROI、帧率或参数是否被当前设备支持；保留错误码。 |
| 有 `img`，没有跟踪框 | 绿色目标是否在视野和 ROI 内、亮度和清晰度、传统检测筛选结果；`track` 只在跟踪目标时更新。 |
| 误差看起来方向不对 | 相机旋转与安装方向、像素误差符号、电控理解的方向，逐项对齐。 |
| GUI / Qt 显示错误 | 是否在本地已登录桌面、环境变量和 OpenCV GUI 后端是否正常。原代码在多个工作线程中调用窗口接口，若实机暴露线程问题需另行记录。 |

## 7. “自启动”到底是什么意思

`Dart_upstart.sh` 是**启动脚本**：它负责准备路径和运行环境、启动程序，程序输出直接显示在终端。原脚本曾把输出追加到原作者目录里的日志文件，本次改为便于手动联调的终端输出。把脚本放在项目目录里，不会自动让它随电脑启动。

“自启动”还需要另一个启动机制来调用这个脚本。对本项目这种会弹出 OpenCV 窗口的程序，桌面登录启动项比较容易继承当前用户的图形会话。仓库的 `config/autostart/dart.desktop.in` 只是模板，模板放在仓库里也不会自行生效；后续需要把 `@DART_ROOT@` 替换成实际项目路径，并安装为当前用户 `~/.config/autostart/` 下的 `.desktop` 文件，才会在用户登录桌面时执行。本次先准备模板，不自动安装。这种登录后启动语义见 [freedesktop 自启动规范](https://specifications.freedesktop.org/autostart/latest/)。

这也意味着“登录后自启动”和“按下电源键后无人登录也能运行”是两个不同阶段。若希望上电后自动登录桌面再启动程序，还涉及 Ubuntu 的自动登录设置、是否接显示器及图形桌面是否能够建立。HDMI 欺骗器只是某些无显示器环境下帮助显卡识别显示设备的一种办法，不是所有小电脑都必需，也不会自动配置登录和程序启动。

systemd 负责管理进程和服务；OpenCV 窗口能否出现，还依赖运行用户、图形会话和显示权限。截图里改用桌面启动项，是为了贴合需要显示窗口的运行场景，不能理解为“所有 systemd 启动的程序都不能显示窗口”。

先完成手动验收，再设置自启动，发生故障时才容易区分是程序本身问题还是启动时机、环境或设备尚未准备好。

## 9. 学习重点

1. **构建配置、运行配置和算法逻辑是不同层次。** CMake 选项决定哪些分支编进程序；JSON 只有在对应代码读取它时才会生效。
2. **绝对路径与工作目录决定资源能否被找到。** 原作者目录不能直接沿用，相对路径则需要明确起点。
3. **先分段验证，再连整条链。** MVS 验证采集，串口工具和电控验证数据，项目验证识别跟踪，最后验证自启动。
4. **字段名不等于物理单位。** 当前 `yaw_error` 是像素，必须从计算式确认单位和方向。
5. **源码是当前行为的依据。** 截图说明、结构体注释和 JSON 中存在的字段，都需要与真正执行的代码相互核对。
